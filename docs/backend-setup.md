# Окремий backend та адмінка 3DiViDruk

Backend не підключається до BB610 Market. Потрібен Python 3.11 або новіший; додаткових пакетів немає.

З кореня репозиторію:

```powershell
$env:DIVIDRUK_ADMIN_TOKEN = '<унікальний випадковий токен щонайменше 24 символи>'
python -m backend.server
```

Відкрийте `http://127.0.0.1:8080/` та `http://127.0.0.1:8080/admin/`.
Токен адміністратора вводиться в адмінці та живе лише в пам’яті відкритої сторінки.
За відсутності токена доступ до приватних API закритий; стандартного пароля немає.
Приклад змінних у `backend/.env.example` — довідка, автоматичного завантаження .env немає.

За замовчуванням увімкнений **тестовий режим**: замовлення позначаються тестовими, реальних оплат, повідомлень чи ТТН немає. Суми перераховуються на сервері за SKU; передані клієнтом ціни ігноруються. Доставка має невідому суму до підтвердження за тарифами перевізника.

Дані лежать в окремому `backend/runtime/3dividruk.sqlite3`; можна задати приватний абсолютний `DIVIDRUK_DB_PATH`. Runtime не публікується та не обслуговується статичним сервером. Ніколи не спрямовуйте цю змінну на базу іншого магазину.

## Що працює

- Публічний каталог із `data/catalog.json` та незалежних локальних змін адмінки.
- Редагування назви, опису, ціни, наявності й відомого залишку товару.
- Серверне створення замовлень, перевірка SKU/наявності/кількості, захист від повторного створення через `Idempotency-Key`.
- Публічний статус тільки з випадковим токеном; без контактів покупця.
- Перегляд замовлень, історія переходів статусів, ручне внесення ТТН.
- Ручне введення відділень Нової пошти й Укрпошти; за окремого серверного ключа — пошук міст/відділень Нової пошти.
- Післяплата зі статусом `pending`. Онлайн-оплата повністю вимкнена.
- GitHub Pages показує каталог і перегляд адмінки. Зміни та приватні дані доступні лише через backend.

## Перед прийманням справжніх замовлень

Розмістіть backend на окремому сервері з TLS, резервними копіями приватної бази та процесним менеджером. Вбудований Python HTTP-сервер призначений для перевірки й невеликого окремого запуску за налаштованим reverse proxy; інфраструктура хостингу не створена автоматично.

Звірте каталог, залишки, реквізити, правила післяплати/доставки, політики магазину та контакти. Після завершення перевірки оператор має задати `DIVIDRUK_TEST_MODE=0` в оточенні серверного процесу та ввімкнути приймання замовлень в адмінці. Без обох кроків справжні замовлення не приймаються. Онлайн-оплата й створення ТТН цим не вмикаються.

У цьому випуску немає еквайрингу, фіскалізації, автоматичних повідомлень, синхронізації з приватним Prom API та автоматичного резервування залишків між каналами. Prom продовжує незалежно приймати замовлення; дані нового каталогу — знімок, а не безперервна синхронізація.

## API

`GET /api/v1/catalog`, `GET /api/v1/payments/methods`, `GET /api/v1/delivery/providers`.

`POST /api/v1/orders` з заголовком `Idempotency-Key` (8–128 символів) та тілом:

```json
{
  "customer": {"name": "Тестова покупка", "phone": "+380970000000"},
  "items": [{"sku": "SKU0001", "quantity": 1}],
  "fulfillment": {"provider": "nova_poshta", "service": "branch", "city": "Дніпро", "branch": "Відділення 1"},
  "payment": {"method": "cod"},
  "test_order": true
}
```

`GET /api/v1/orders/{order_id}?token={public_token}`. Бережіть токен: він дає доступ до статусу конкретного замовлення.

Адмінські запити потребують `Authorization: Bearer <DIVIDRUK_ADMIN_TOKEN>`:
`GET /api/v1/admin/orders`, `GET /api/v1/admin/catalog`, `GET/PATCH /api/v1/admin/settings`,
`PATCH /api/v1/admin/catalog/{sku}`, `PATCH /api/v1/admin/orders/{order_id}`.

## Перевірка

```powershell
python -m unittest discover -s tests -p backend_test.py -v
```

Тести створюють лише тимчасові бази та каталог і працюють через localhost. Реальних платежів і звернень до перевізника не виконують.
